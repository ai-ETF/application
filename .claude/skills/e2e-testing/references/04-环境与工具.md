## 一、工具选型结论

**用 `@dcloudio/uni-automator` + jest。**

**决定性理由：它已经在 `application/package.json` 的 devDependencies 里了**，版本与其余 17 个 `@dcloudio/*` 包完全一致（随 uni-app 官方同步发布）。不需要引入任何第三方工具。

**另一个契合点**：它的 mock API 是 **`uni.` 前缀**（`mockUniMethod` / `callUniMethod`），而本项目代码里用的正是 `uni.showModal` / `uni.showToast` / `uni.setStorageSync` → **不用做 `wx.` ↔ `uni.` 适配**，桩的粒度与代码调用点一一对应。

**没选的，以及为什么**（细节见 `docs/e2e/04-工具选型.md`）：

| 方案 | 为什么不用 |
|---|---|
| `miniprogram-automator`（裸用） | 微信官方 SDK，**自 2023-11 停更**；社区曾记 `launch()` spawn EINVAL 与 `Page.*` 协议族整族超时两处硬伤 —— ⚠️ 但 **`Page.*` 超时在本机已被证伪**（2026-10-03 实测 `$` / `$$` / `input` / `tap` 全部可用），详见下节 |
| `Minium`（Python） | 唯一能塞进 pytest 栈的方案（同为 Python），但仍是 beta（`1.0.0b2`）、**URL 直装不走 PyPI**（与 poetry 规范冲突，只能装独立 venv）。**Plan B 保留**：jest 27 已在 Node 22 上实测跑通（见 §四），**目前不需要切它** |
| 微信云测 | 每周 150 分钟免费、专有云 1600 元/台/月；**跑在云真机上、本机 CI 无法编排**，且会打到 `API_BASE` 配的后端（当前是生产）→ 等于对生产库做真实交易 |
| H5 端 + Playwright/Cypress 代跑 | ⭐ H5 与小程序是**两条不同代码路径**（H5 走 `fetch` + `ReadableStream`，小程序走 `uni.request` + `enableChunked` + `onChunkReceived`）。**风险最高的正是小程序那一支**，用 H5 跑等于把风险排除在覆盖外。可作补充，不可作替代 |

## 二、执行拓扑（WSL 的坑）

**实测事实**：本机是 WSL2（`uname -a` 显示 `microsoft-standard-WSL2`）；微信开发者工具是 Windows 应用（默认安装路径在 WSL 里查不到）。

**问题链条**：
1. uni-automator 对 mp-weixin 的处理是 **spawn 开发者工具的 `cli.bat`**，并通过 **WebSocket 连 `ws://127.0.0.1:9420`** 驱动它。
2. WSL2 的 localhost 转发是 **Windows → WSL 单向可用**。
3. devtools 的 9420 **只监听 Windows 侧 127.0.0.1** → **WSL 里的 jest 连不上**。

**→ 推荐拓扑**（业务代码全留 WSL，只有测试运行器在 Windows）：

```
┌─ WSL2 ─────────────────────────┐      ┌─ Windows ───────────────────────┐
│ 后端 uvicorn  :8000             │◄─────┤ 微信开发者工具 + cli.bat :9420   │
│ pytest / 契约测试 / fixture      │      │ jest + uni-automator            │
│ poetry / Node 22（开发用）       │      │ Node 16/18（E2E 专用，见第四节） │
└────────────────────────────────┘      └─────────────────────────────────┘
        ▲  Windows→WSL localhost 转发可用  ▲  同机 127.0.0.1 直连
```

- ✅ Windows → WSL 的 `http://localhost:8000` 可用 → 小程序能打到 WSL 里的后端。
- ❌ 反向不可用 → **jest 必须在 Windows 上运行**，`application` 仓库需要在 Windows 侧也有一份。
- 想在 WSL 里跑就得在 Windows 上做 `netsh portproxy` 转发 9420 → **不建议**（多一层会坏的环节）。

**区分两个端口**：**9420 是自动化端口**（automator 用）；**服务端口**（如 55975）用于 CLI 登录/预览/上传。在开发者工具「设置 → 安全设置 → 服务端口」里开启自动化测试。

## 三、jest 配置

`application/jest.e2e.config.js`（独立文件，不要和将来前端单测的 vitest 配置合并）：

```js
module.exports = {
  globalTeardown: '@dcloudio/uni-automator/dist/teardown.js',
  testEnvironment: '@dcloudio/uni-automator/dist/environment.js',
  testEnvironmentOptions: {
    compile: true,                 // 自动编译，不需要单独的 build 步骤
    'mp-weixin': {
      port: 9420,
      launch: true,
      teardown: 'disconnect',      // 保留 devtools，避免每轮冷启动 6~12s
      remote: false
      // executablePath: 自动查找失败时才填
    }
  },
  testTimeout: 30000,              // 全局；SSE 用例内部单独设 130000
  testMatch: ['<rootDir>/e2e/**/*.e2e.js'],
  watchPathIgnorePatterns: ['/node_modules/', '/dist/', '/.git/']
}
```

```jsonc
// package.json 里实际用的三条（2026-10-03 起已就位）
"scripts": {
  "e2e:patch": "node e2e/patches/apply-node-modules-patches.js",
  "e2e:patch:check": "node e2e/patches/apply-node-modules-patches.js --check",
  "test:e2e": "npm run e2e:patch && cross-env UNI_PLATFORM=mp-weixin DEBUG=automator:* DEBUG_COLORS=0 jest -i --config jest.e2e.config.js"
}
```

**`test:e2e` 开跑前会先应用 node_modules 补丁**（见 §四），所以换机器/重装依赖后直接跑这一条即可，
不需要手工改任何文件。`DEBUG=automator:*` 是为了拿到 `automator:runtime connected` 那行 ——
**它是判断「小程序真的起来了」的唯一可靠信号**，别只看用例结果。

**API 要点**：
- uni-automator 通过 `testEnvironment` **注入全局 `program` 对象**（不需要手动 launch）。
- 取页面：`program.currentPage()`；导航：`program.reLaunch(...)`。
- mock：`program.mockUniMethod('showModal', {...})` / `program.restoreUniMethod(...)`。
- 调 uni 方法：`program.callUniMethod('setStorageSync', ...)`。
- `program.evaluate` **仅在开发者工具模拟器可用**，且**无法闭包引用外部变量**。

**微信端硬限制**：
- **element 不能跨组件选择**，**不支持父子选择器** → `page.$('.a .b')` 无效，要分两次 `$`。
- 分包页面 `reLaunch` 后需 `await page.waitFor(7000)` 再取 `currentPage()`。**本项目未配置分包**（`pages.json` 无 `subPackages`），暂不受影响 —— 但改动 `pages.json` 时要留意。
- `testMatch` 必须与前端单测（vitest）**分开**，否则 `npm test` 会互相抢文件。

## 四、版本风险（**已实测排除**，留作换机器时的对照）

| 事实 | 后果 |
|---|---|
| uni-automator 要求 **jest ≤ 27.0.4**、`jest-environment-node ≤ 27.5.1` | 必须装 jest 27 |
| 本机 `node -v` = **v22.21.0** | **jest 27 官方支持的 Node 范围是 10/12/14/15/16**，**不含 22** |
| jest 27 的传递依赖在 Node 18+ 有已知告警/报错 | 可能启动即崩 |

> ✅ **2026-09-30 实测结论：Node v22.21.0 + jest 27.0.4 跑得通**，P4 全套连跑两轮全绿
> （`2 skipped, 5 passed, 7 total`）。**不需要 nvm 隔离，Plan B（Minium）不启用。**
> 上表那三条"可能崩"的担心**没有发生** —— 支持列表不含 Node 22 ≠ 一定跑不了。

**处置顺序（若换机器后复现问题）**：
1. 先在这台机器上直接试 Node + jest 27（这才是真实条件，别凭支持列表预判）。
2. 跑不通 → Windows 侧用 `nvm-windows` 装 **Node 16 或 18** 作 E2E 专用，与开发用的 Node 隔离。
3. 都不行 → 切 **Plan B（Minium）**。

> ✅ **2026-10-03 澄清：`jest` / `cross-env` 本来就是可复现的，不需要写进 `package.json`。**
> 早先「没记进 `package.json`，换机器就装不上」的说法是**错的**。实测：只拿 `package.json` + `package-lock.json`
> 在空目录 `npm ci`，装出来的正是 `jest 27.0.4` + `cross-env 7.0.3` + `jest-environment-node 27.5.1`，二进制也在 `.bin/` 下。
> 原因：`@dcloudio/uni-automator` 把 `jest` / `jest-environment-node` 声明为 **peerDependencies**（**精确版本**，不会漂），
> `cross-env` 是它的**直接依赖** —— npm 7+ 会自动装 peer + 提升传递依赖。
>
> ✅ **真正需要固化的只有 node_modules 补丁，2026-10-03 已固化**：
> 精确核实为 **2 个文件、4 处改动**（做法：拿一份干净重装的 `node_modules` 逐文件比对，
> 24692 个文件里只有这 2 个不同）。写成幂等脚本 `application/e2e/patches/apply-node-modules-patches.js`，
> 由 `npm run test:e2e` 自动应用。**故意不做 `postinstall`** —— 那两个文件只有 E2E 才走到。
>
> ⚠️ **补丁的根因不是「中文路径」**：Node 自 18.20.2 / 20.12.2 / 22 起为堵 BatBadBut（CVE-2024-27980），
> **不带 `shell: true` spawn `.bat` 会抛 EINVAL**。补了 `shell: true` 之后命令要过 cmd.exe，
> 路径里的空格和中文才**跟着**需要加引号 —— 4 处是一套，不能只挑一半。
> 版本升级后如果锚点字符串找不到了，脚本会**报错退出**而不是瞎改，此时需重新确认补丁点。

**另一个已知故障族**（症状与处置）：
- ⭐ **`Failed to connect to runtime`、0 个用例执行、项目窗口日志停在 `routeTo appLaunch timeout`**
  → **第一反应查 9420 有没有被 `Listen`**（`Get-NetTCPConnection -LocalPort 9420`，WSL 的 `netstat` 看不到 Windows 端口）。
  9420 被占 → 开发者工具执行 `auto --auto-port 9420` 时抛 `Port 9420 is in use` → **静默走不到 openProject**
  → 项目不重开、小程序不跑 → 白等 timeout 才报这句。
  **别去猜「界面上有弹窗挡着」** —— 2026-10-03 我这么猜过，是错的（`EnumWindows` 枚举确认没有 `#32770` 弹窗）。
  **也先读 `jest.e2e.config.js` 的注释**，这个机制就写在那里。
- `launch()` `spawn EINVAL`（Node 24 + Windows，BatBadBut 相关）→ 绕过 `.bat`，直接 spawn 同目录的 `node.exe + cli.js`。
- **`Page.*` 报 `page destroyed` / 看起来"挂起"** → ⚠️ **曾经**被诊断为「SDK 与开发者工具的版本错配，要换 devtools 版本」，
  **这个诊断是错的**（2026-10-03 在本机 `Stable v1.06.2504040` 上实测证伪）。真相是：
  `program.currentPage()` 可能交回一个**站在页面跳转窗口期**上的 page（典型场景：应用启动时
  `pages/index/index → pages/login/index` 的自动跳转）。此时开发者工具回 `{"error":{"message":"page destroyed"}}`。
  **正确处置**：① 取 page 前先等页面稳定（轮询 `currentPage()` 直到 `path` 不再变，`waitForPage` 就是干这个的）；
  ② 别据此去换 devtools 版本、更别改用例。
- **"亚秒级 launch 成功"是坏信号**：devtools 被 kill 后不会立即释放 9420，残留会话会让 `launch()` 在 0.4s 内假连上。正常冷启动需 **6.5–12.3 秒**。

### automator 能力矩阵（2026-10-03 本机实测，可放心用）

| 能力 | 结论 |
|---|---|
| `program.evaluate()` | ✅ 可用 |
| `page.$` / `page.$$`（含 **class 选择器**） | ✅ 可用 |
| `el.input()` | ✅ **真的写进 Vue 的 v-model**（证据：填完两个输入框后按钮 class 的 `--disabled` 消失） |
| `el.tap()` | ✅ 可用 |
| `el.attribute('class')` / `el.text()` | ✅ 可用（断言的抓手） |
| `page.data()` | ⚠️ 可用但返回 `{}` —— uni-app Vue3 的业务状态不在 `page.data` 上 |
| 读 Pinia store | ✅ `$vm.$pinia.state.value` 直接可读（**不需要**前端加 `getApp().globalData.__xxx` 钩子） |
| `mockUniMethod` 结果式 | ✅ 可用 |
| `mockUniMethod` **函数式**（捕参数） | ❌ 仍不可用（`(intermediate value) is not a function`） |
| 网络层 / SSE 帧 | ❌ 协议没有（与版本无关，是能力边界） |

> ⚠️ 不要再用「元素查询不可用」来解释某条用例写不出来 —— 那是**早期基于错误诊断的结论**，
> 已在 2026-10-03 被推翻。写不出来要先问「选择器定了吗」「页面稳定了吗」。

> **9420 的占用从哪来**：`teardown: 'quit'` 会正常放掉端口（跑完变 `TimeWait`、`Listen` 消失），
> 但**进程不退** —— 实测一轮成功后仍留 9 个 `wechatdevtools`。**残留进程本身无害**
> （不杀进程直接跑第二轮也全绿）；真正致命的是**中途被打断的运行**留下的、仍 `Listen` 着 9420 的孤儿进程。
> 所以规则是「**开跑前 9420 不能有 `Listen`**」，不是「每轮必须杀进程」。
> 省事手段：`taskkill /F /IM wechatdevtools.exe` 一次杀光。

## 五、必须锁死的东西

- **开发者工具的版本号**：登记进文档（本机登记值 `Stable v1.06.2504040`），并建议**关掉自动更新**。
  理由现在是**可复现性**，⚠️ **不是**「某些 bug 是版本错配引起的」—— 那个因果关系已被证伪。
- `Page.*` 出问题时**不要**先想着换 devtools 版本。顺序是：
  ① 查 9420 有没有被 `Listen`；② 确认取 page 时页面已经稳定（别站在跳转窗口期上）。

## 六、前端阻塞性前置

| 项 | 现状 | 必须做什么 | 阻塞什么 |
|---|---|---|---|
| ⭐ `API_BASE` | **硬编码生产** `https://ai-etf.xyz`，`.env*` 三个文件全 0 字节 | 改成读环境变量并**保留现值为默认** | **阻塞全部 E2E**。不改则会对生产库做真实申购 |
| `urlCheck` | `true`（`src/manifest.json` 的 `mp-weixin.setting`） | **新增 `src/project.private.config.json`**，写 `"urlCheck": false`（见下） | 拦 `http://localhost:8000` |
| `appid` | `wx4345af65c586dd70`（真号）。**2026-10-03 起本机账号已拿到开发者权限** | 同一个 private config 里写 `"appid": "touristappid"`（**权限到手了仍保留游客模式**，理由见下） | 无权限时开发者工具**根本打不开项目**（code 10），而报出来的是 `please make sure http port is open` |

> ⚠️ **`project.private.config.json` 必须放在 `application/src/`，放仓库根目录不生效。**
> uni 的拷贝清单（`@dcloudio/uni-mp-weixin/dist/uni.compiler.js:211-232` 的 `copyOptions.targets`）
> 里的路径是相对**编译入口目录**（`src/`）解析的。放根目录的文件**不会进产物**，
> 而开发者工具打开的是**产物目录**，自然读不到。
> **2026-10-02 实测**：放根目录 → dist 里没有这个文件；放 `src/` → 出现且生效。
>
> 文件内容至少要有这两项：
> ```json
> { "appid": "touristappid", "setting": { "urlCheck": false } }
> ```
> 开发者工具读配置的规则是 **private 覆盖 public**（`project.config.json` 是公共层，
> `project.private.config.json` 是个人层，微信为此专门加的一层）。
> 所以断言要看**合并后**的值，别只看 uni 生成的 `project.config.json` ——
> 那个文件里永远是真 appid + `urlCheck: true`，因为它是从 `src/manifest.json` 生成的。
>
> **为什么走 private config 而不是 `src/manifest.json`**：`manifest.json` 是**已跟踪、全组共享的源码**，
> 往里写测试用的 appid 等于把它焊死进仓库、影响所有人的本地开发；private config 一行源码都不动。
> ⚠️ 我们一度得出「必须改 `src/manifest.json`」—— **那是个错误结论**，不是 private config 这条路不通，
> 是当时把它放错了目录（放在仓库根，而不是 `src/`）。`manifest.json` **一行都不用改**。
>
> ⚠️ **appid 的报错信息是误导的**：真 appid + 无权限 → 开发者工具问微信要权限 → 被拒（code 10）
> → CLI 直接退出 → uni-automator 报 **"Failed to launch Wechat web DevTools, please make sure http port is open"**。
> 这句话**跟端口一点关系都没有**，是权限问题。看到它先查 appid，别往端口方向查。
> 用 CLI 手跑一次就能看到真话：`cli.bat auto --project <产物目录> --auto-port 9420`。
>
> 验收：重编译后 `dist/dev/mp-weixin/project.private.config.json` 应该存在。
> `e2e/helpers/env.js` 的 `assertUrlCheckDisabled()` / `assertTouristAppId()` 会自动读**合并后**的配置拦一道。
>
> 两点补充：
> - `urlCheck` 只管**本地开发**，发布后的域名校验由微信服务端强制，关掉不构成线上风险。
> - ⚠️ **`urlCheck: false` 的必要性没被证明**（2026-10-03 复核）：把它设回 `true`（此时生效 appid 是真号），
>   **整套 P4 依然全绿** —— 其中包括必须先拿到服务端 401 才能通过的 P4-02，说明请求确实发出去了。
>   也就是说当前配置下开发者工具**可能本来就放行 localhost**。
>   保留 `urlCheck: false` 是零成本保险（换真 appid / 换机器时更可能需要），
>   **但别把「必须关 urlCheck」当成已证事实写进结论。**

> **appid 为什么权限到手了还用游客模式**：权限是**跟着账号走**的，而
> `src/project.private.config.json` 是要**提交给所有人用**的 —— 写 `touristappid` 谁 clone 下来都能跑；
> 写真号则只有有权限的账号能跑，别人一跑就撞上那句误导性报错。
> **代价**：游客模式下会报 `gettestpublib Error 41002, appid missing`（**已证实不影响跑通**），
> 拿不到测试库/发布能力 —— 那两样 E2E 不用。
> **切真号**：改 `"appid"` 这一行即可，前提是跑测试的账号有开发者权限；需要测**与 appid 绑定**的
> 能力时（`wx.login` 的真实 code、云能力）才需要切。

> **未完成 `API_BASE` 改造前，只允许跑 P4（只读 + 登出），禁止跑 P1 / P5（会写数据）。**

## 七、与后端 pytest 栈的配合

选 uni-automator 就意味着**两套运行器**（这是它唯一的代价）：

| 受众 | 命令 |
|---|---|
| 后端 | `poetry run pytest`（含 L3 契约测试，marker `contract`） |
| 前端 | `npm run test:e2e` |

**桥接方式**：
1. **夹具复用后端能力**：`ai-etf/docs/e2e/scripts/e2e_fixture.py` 提供 `register` / `token` / `cleanup`，前端 E2E 通过 `execSync` 调用它 → 前端仓库不写任何后端逻辑。（**没有 `confirm-pending`**，理由见 [参考 02 §四](02-夹具与断言设计.md)。）
2. **交叉断言**：E2E 用夹具 token 直连后端读真值比对 UI，天然把两仓库串起来。
3. **统一用例编号**（`P1-03` 这种）：两套报告靠编号拼成一张总表。
4. **CI 编排**：L3 与 L4 分开 job，L4 需要 **Windows runner**。

**marker 约定**（后端）：现有 `addopts = "-m 'not integration and not eval'"` 是**黑名单**，所以新增的 `contract` marker 会**默认运行** —— 正合适，因为契约测试大多是静态断言（读 `app.routes` / `openapi.json`），不联网、不碰数据库。需要真实响应字节的那条（SSE 帧契约）复用已有的 `integration_net`（默认不跑）。**只新增一个 marker，不破坏现有体系。**

## 八、起后端时必须带行情夹具

**任何涉及行情的用例（P3 全部）跑之前，后端必须这样起**，否则搜索返回 0 条、
`realtime` 是 null，用例会以「数据为空」的方式变红 —— 而**看起来像是你用例写错了**：

```bash
cd ai-etf
E2E_MARKET_FIXTURE="$PWD/docs/e2e/fixtures/market_snapshot.json" \
  poetry run uvicorn server.app:app --port 8000
```

看到这两行才算成功（第二行夹具关闭时是 `共 0 只ETF`）：

```
[market_fixture] ⚠️ 行情夹具已启用：akshare 的 8 个行情函数已被固定快照替换（快照：...）
哈希表构建完成，共 3 只ETF
```

**原理**：`server/services/market_fixture.py` 在设了环境变量时，把 akshare 的 8 个行情函数
在**模块层**换成读固定快照的实现 → 页面、store、`request.ts`、schemas 全都保持真实，
只有最上游的数据源被替换。**不设环境变量 = 完全现有行为**（连 `import akshare` 都不执行）；
**设了但快照文件不存在 → 启动直接抛错**（故意的，别把它当 bug）。

**⚠️ 三件必须记住的事**：

1. **冷启动约 4 分钟**（`server.api.upload` 那个 import 占 250s，是软工作业链路）。
   别以为服务挂了，`ps` 看得到进程就是还在起。
2. **改了 `market_snapshot.json` 里的 K 线，要 `rm -rf /tmp/etf_kline_cache`** 才生效
   （1 天文件缓存挡在前面）。
3. **K 线数值断言用 `toBeCloseTo(x, 3)`，别用 `toBe(x)`** —— `pd.read_json()` 会引进 1 ULP
   误差：清缓存后第一次请求 `high=3.82`，命中缓存的第二次就变成 `3.8200000000000003`。
   spot / search 走内存缓存，不受影响，可以精确断言。

夹具的完整说明（快照里有什么数据、怎么重新生成、`--capture` 抓真实数据）
见 `ai-etf/docs/e2e/09-P3阻塞与数据夹具建议.md` §5。
